# MVP familiar Implementation Plan

> **For agentic workers:** Use subagent-driven-development or executing-plans para implementar y revisar cada bloque. Este documento sustituye decisiones de alcance incompatibles de agosto, pero conserva su evidencia histórica.

**Goal:** Entregar el MVP solicitado el 31 de octubre, empezando por Wishlist y conservando privacidad verificable entre personas y familias.

**Architecture:** Mantener rutas SvelteKit, servicios de dominio y Supabase con RLS como frontera definitiva. Migraciones incrementales y transacciones para operaciones relacionadas; no reemplazar la arquitectura existente.

**Tech Stack:** Svelte 5, SvelteKit 2, TypeScript, Supabase, pnpm, Node 24, Docker, Vitest, Playwright y pgTAP.

## Estado y regla de cierre

Estado: MVP funcional implementado y verificado en local; lanzamiento abierto por controles de seguridad y operación, configuración y validación externa. El cierre de agosto corresponde a otro alcance y no demuestra este MVP. No se ejecutará `db reset` sobre una instancia del usuario. La importación Excel queda para un hito futuro y requiere el archivo y mapeo de emails.

## Paralelismo y continuidad

Durante QA local se observaron aproximadamente 1,9 GiB de uso Docker para Supabase, incluidos Studio y analytics, además de Node y ClamAV. ClamAV midió 955.9 MiB idle, dato que no garantiza su uso en carga. La guía de seguridad de carga recomienda 3 a 4 GiB para el motor. No dimensionar el VPS con la medición idle.

Cierre anterior: 314 pruebas unitarias en 54 archivos, `pnpm check` con 0 errores/17 avisos y lint con 0 errores/73 avisos. El análisis oficial local de Svelte revisó 40 archivos sin incidencias; las 26 sugerencias I/O antiguas de juegos se revisaron y conservaron. El ciclo de backup Linux pasó 11/11 pruebas mock (`output/backup-cycle-linux.log`), el helper Docker real terminó con código 0 y las pruebas criptográficas pasaron 4/4. Las 900 aserciones DB pertenecen a la línea base anterior. La suite E2E completa pasó 38/38 en una ejecución final sobre Docker endurecido y Caddy, 19 desktop/19 móvil, sin reintentos ni omisiones (`output/e2e-final-docker-once.log`).

La ejecución inicial de 36 E2E pasó 36/36 (`output/e2e-navigation-full-once.log`). Una suite diagnóstica encontró y permitió corregir problemas de CSP en formulario/descarga, avatar previo a hidratación y navegación de Wishlist durante una mutación; la suite final pasó 38/38. No se atribuye un resultado rojo/verde determinista al caso de Wishlist. Docker/Caddy usaron HTTP local, por lo que la prueba no acredita TLS real.

La revisión manual de listas cubrió 393 y 1280 px en claro y oscuro, sin desbordamiento, y comprobó autorrelleno de cantidad/unidad y formulario de plantilla (`output/lists-visual-report.json`). El analizador oficial de Svelte revisó 37 archivos sin incidencias; las 26 heurísticas I/O heredadas de juegos se revisaron y conservaron.

La revisión manual en navegador cubrió anchos de 393 y 1280 px y temas claro y oscuro; teclado activó filtros y selector de tema, no hubo overflow y CSRF autenticado desde origen hostil respondió 403 en ambos temas. El contraste secundario medido fue 5.38:1 en claro y 6.72:1 en oscuro; se ajustó el color secundario y el avatar neutral conserva contraste legible.

El lanzamiento aún requiere credenciales OAuth reales, SMTP, verificación de límites remotos/antiabuso de Auth/API, TLS real y copias programadas/externas. La importación Excel espera al archivo y al mapeo de emails. La sincronización automática y el SaaS comercial corresponden a hitos futuros.

Infraestructura y seguridad web pueden avanzar simultáneamente con auditoría de dominios. Las migraciones, tipos generados y archivos compartidos tienen un único responsable por bloque. Cada continuación debe leer este plan, los informes de auditoría y `git diff` antes de delegar. No volver a ejecutar trabajo marcado como verificado salvo cambios relevantes.

Modelos: Luna ligero para inventario/ediciones sencillas, Sol ligero para infraestructura moderada y Sol medio (variante GPT 6.1 disponible) para permisos y seguridad compleja. No se necesita Astra para el alcance de planificación de esta revisión.

El bloque posterior de recuperación, operación y listas está implementado y cerrado en local; consultar [su plan](2026-10-31-recovery-operations-lists.md). La preparación no acredita despliegue ni servicios externos reales.
